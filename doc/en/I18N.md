# I18N.md — Calculia multilingual architecture

> 🌐 **Other languages:** [Español](../es/I18N.md)

Technical reference of the internationalization system (`App.i18n`)
and the step-by-step recipe to add a new language. Read alongside
[`technical.md`](technical.md) §3 (shared core) and
[`SPEC.md`](SPEC.md) §3–§4 (product and accessibility rules, which
apply **in every language**).

**Current state**: Spanish (`es`, default) and English (`en`). The
system has been **designed for more than two languages** from the
start: keys are always in English (technical code), values are the
translatable UI text, and detection (`navigator.languages`) and
persistence (`localStorage`) do not assume a fixed number of locales.
A few `es`/`en` binary spots still remain (number format, time
expressions, the landing selector, the wallet decimal separator) that
need to be generalized when adding a third one — see §4.

The hidden routes (`settings/`, `legal/`, see `technical.md`) follow
the same multi-file pattern described here, not a special case.

**Language policy**:

- **User interface (UI)**: multilingual — every text visible to the
  end user exists in every supported language (`es`, `en`…).
- **Technical code**: **always in English** — variable, function and
  JS-object names, and **crucially the keys in `strings.<locale>.js`**
  must be in English. The values of those keys are the translatable UI
  text, but the key itself is code, so it is in English.

  ```js
  // ✅ Correct — English key, values in the file's language
  // tools/numbers/strings.es.js
  App.i18n.register({
    levelTitle: 'Elige el nivel', introText: 'Cuenta los objetos'
  }, 'es');
  // tools/numbers/strings.en.js
  App.i18n.register({
    levelTitle: 'Choose a level', introText: 'Count the objects'
  }, 'en');
  ```

  This split keeps `App.i18n.t('levelTitle')` readable in the source
  code, regardless of the active language.

## 0. Multi-file system

Texts for each activity/landing are split **by language** in separate
files, instead of a single `strings.js` with `{es: {...}, en: {...}}`.

### Structure

```
site/strings.es.js                    ← Spanish only (registers in locale 'es')
site/strings.en.js                    ← English only (registers in locale 'en')

tools/numbers/strings.es.js           ← Spanish for the Numbers activity
tools/numbers/strings.en.js           ← English for the Numbers activity
tools/quantities/strings.es.js        ← Spanish for Quantities
tools/quantities/strings.en.js        ← English for Quantities
... (same pattern for all 14 activities)

settings/strings.es.js                ← Spanish for the progress panel
settings/strings.en.js                ← English for the progress panel
legal/strings.es.js                   ← Spanish for the legal page
legal/strings.en.js                   ← English for the legal page
```

### Advantages over the monolithic file

- **Only the active language is loaded**: before, both languages were
  sent to the end user (double download). Now only the locale's files
  are downloaded.
- **Independent maintenance**: a translator only edits the file of
  the language they know — they do not see the other language mixed in.
- **Cleaner diffs**: an English translation change shows only the
  English lines that changed, not the whole file.
- **Scalability**: adding a language is just creating
  `strings.<locale>.js` per activity, without touching the other
  languages.
- **Better caching**: the browser caches per language; switching
  language reloads from cache without re-downloading both.

### `strings.<locale>.js` pattern

```js
/* ============================================================
   Calculia — Numbers texts (EN)
   Per-language file. Loaded synchronously from index.html
   after i18n.js.
   ============================================================ */
(function () {
  'use strict';

  App.i18n.register({
    title: '🧮 Numbers',
    instruccion: 'Count the objects and pick the right amount.',
    // ... rest of EN keys
  }, 'en');
})();
```

The second argument of `register(dict, locale)` indicates **which
language** to register. `App.i18n.js` stores it in `DICT[locale]` and
keeps the fallback to Spanish when a key is missing.

## 1. Pieces of the system

```
assets/js/i18n.js             # Core: App.i18n (detection, persistence, t/pick/apply)
assets/js/dinero.js           # Core: money texts (also multilingual)
site/strings.es.js            # Landing texts (ES)
site/strings.en.js            # Landing texts (EN)
site/index.html               # Language selector + conditional load
tools/<slug>/strings.es.js    # Activity texts (ES)
tools/<slug>/strings.en.js    # Activity texts (EN)
tools/<slug>/data.js          # Data: some indexed by locale, others shared
tools/<slug>/app.js           # Uses App.i18n.t()/.pick()/.locale() to read/generate text
tools/<slug>/index.html       # Loads strings.<locale>.js per App.i18n.locale()
settings/strings.<locale>.js  # Progress panel texts (same pattern)
legal/strings.<locale>.js     # Legal page texts (same pattern)
```

### 1.1 `assets/js/i18n.js` — core

```js
var SOPORTADOS  = ['es', 'en'];   // activatable languages
var POR_DEFECTO = 'es';           // fallback when a key is missing or the detected language is not supported
var BCP47       = { es: 'es-ES', en: 'en-US' };  // for speechSynthesis
```

- **Detection** (`detectar()`): walks through `navigator.languages`
  and takes the 2-letter prefix of the first one in `SOPORTADOS`. If
  none matches, it uses `POR_DEFECTO`.
- **Persistence** (`locale()` / `setLocale()`):
  `localStorage['calculia:locale']`. A saved and supported value wins
  over detection. `setLocale()` saves and **reloads the page** (there
  is no hot re-render).
- **`register(dict, locale)`**: new multi-file form, registers in the
  given locale. The legacy form `register({es:{...}, en:{...}})` is
  kept for back-compat.
- **`t(key)`**: looks up `key` (with dots, e.g. `'nivel.c1'` or
  `'core.back'`) in the active language. If missing, falls back to
  `POR_DEFECTO` (Spanish). If still missing, it returns the `key`
  itself (so broken keys are visible on screen). If the value is an
  array, it joins it with `', '` (meant for debugging, not for the UI).
- **`pick(key)`**: like `t`, but for keys whose value is an **array**
  of variants (e.g. `feedback.success`) — returns a random element.
  Used by `feedback.js` for the success/encouragement messages.
- **`apply(root)`**: applies `data-i18n` (→ `textContent`) and
  `data-i18n-aria` (→ `aria-label`) to every DOM node under `root`
  (default `document`). Runs on `DOMContentLoaded`. It also sets
  `document.documentElement.lang` and, if `<html>` has
  `data-i18n-title="key"`, sets `document.title = t(key) +
  ' | Calculia'`.
- **`lang()`**: returns the BCP-47 code of the active locale
  (`'es-ES'` / `'en-US'` today, extensible). Used by `App.tts.speak()`
  to pick the speechSynthesis voice.
- **`data(key)` / `datos()` / `registerStructure()`**: for data trees
  whose text is merged from `strings.<locale>.js` while the structure
  (ids, types, coordinates) lives in `data.js`. Pattern used by
  `numbers`, `riddles`, `wallet`, `clock`, `roman-numerals`,
  `patterns`, `stories`, `odd-one-out` (see `technical.md` §2.1).

### 1.3 `strings.<locale>.js` per tool

Pattern (see `tools/numbers/strings.es.js` as the gold reference):

```js
/* tools/numbers/strings.es.js */
(function () {
  'use strict';
  App.i18n.register({
    title: '🧮 Los Números',
    instruccion: 'Cuenta los objetos y elige la cantidad correcta.',
    maximo: '¿Cuántos hay? Hasta {n}',
    // ... rest of ES keys
  }, 'es');
})();
```

```js
/* tools/numbers/strings.en.js */
(function () {
  'use strict';
  App.i18n.register({
    title: '🧮 Numbers',
    instruccion: 'Count the objects and pick the right amount.',
    maximo: 'How many? Up to {n}',
    // ... rest of EN keys
  }, 'en');
})();
```

**Important**: the keys (`title`, `instruccion`, `maximo`) are
technical code and are always in English, regardless of the UI
language. Values are the translatable text for the user.

- The `title` key must always exist (used by `data-i18n-title` for the
  document `<title>`).
- **Keys must match exactly** between `strings.es.js` and
  `strings.en.js` (verified by `scripts/check.js` §4).
- Brace placeholders (`'{n} veces'`) are substituted manually in
  `app.js` with `.replace('{n}', value)` — **there is no
  interpolation engine**; if the same placeholder appears twice in a
  key, use `.replace(/\{n\}/g, value)`.
- Nested objects work as namespaces: `nivel: { c1: '...', c2: '...' }`
  is read with `t('nivel.c1')`.
- **Never** use an array for position-indexed data (`t()` would join
  the array with commas). For number-indexed tables use an object with
  text keys (`{ 0: '', 1: 'miles', 2: 'millones' }`) and read with
  `t('grupoEtq.' + i)`.

### 1.4 Where the text lives: three patterns for `data.js`

1. **Data indexed by id, text in `strings.<locale>.js`** (recommended
   when most fields are structural: coordinates, colors, level ids…).
   Example: `tools/wallet/data.js` stores the denominations
   (structure) and `app.js` looks up the name with
   `App.i18n.t('dibujo.' + d.id)`.
2. **Parallel data per locale** (`{ es: {...}, en: {...} }`) when
   almost every field is text or differs in background per locale
   (riddles' hints, story texts). Accessed with `App.i18n.data('data')`
   or `App.i18n.datos()` (which rebuilds the `{es, en}` shape by
   merging structure + texts per locale).
3. **Shared data with no duplication**, when it truly does not depend
   on locale: amounts in cents (`DATA.llegaUno` in `wallet`), Roman
   numerals as strings (`DATA.simbolos` in `roman-numerals`).

### 1.5 HTML: `data-i18n*` attributes

```html
<html lang="es" data-i18n-title="title">
...
<h1 data-i18n="title">🧮 Los Números</h1>
<button data-i18n-aria="core.listenInstructions" aria-label="Escuchar las instrucciones">🔊</button>
```

The Spanish text/`aria-label` stays as default content in the HTML
(so the page still makes sense if `i18n.js` fails to load) and
`apply()` overwrites it on startup. Attributes `apply()` **does not**
cover (must be set manually in `app.js` on startup): `placeholder` on
`<textarea>`/`<input>`.

### 1.6 Script load order (mandatory)

```html
<script src="../../assets/js/utils.js"></script>
<script src="../../assets/js/i18n.js"></script>
<script src="../../assets/js/tts.js"></script>
<script src="../../assets/js/storage.js"></script>
<script src="../../assets/js/feedback.js"></script>
<!-- Both locale files load synchronously, no document.write -->
<script src="strings.es.js"></script>
<script src="strings.en.js"></script>
<script src="data.js"></script>
<script src="app.js"></script>
```

`i18n.js` loads before `tts.js`/`feedback.js` (both read the active
locale). The two `strings.<locale>.js` files load synchronously
**before** `data.js` and `app.js`, so `App.i18n.register` already
filled the dictionary when any UI code calls `App.i18n.t()`.
`document.write` is **not** used: Chrome and Firefox process scripts
injected via `document.write` asynchronously, so they would load
*after* `data.js`/`app.js` and `App.i18n.t()` would return literal
keys during the initial render.

### 1.7 Language selector (landing)

`site/index.html` has **two fixed buttons** (not generated from
`SOPORTADOS`):

```html
<div class="idioma-selector" role="group" aria-label="Elegir idioma">
  <button type="button" class="btn-idioma" id="btnIdiomaEs" data-locale="es" aria-pressed="false">🇪🇸 Español</button>
  <button type="button" class="btn-idioma" id="btnIdiomaEn" data-locale="en" aria-pressed="false">🇬🇧 English</button>
</div>
```

with its own JS (`pintarSelectorIdioma()`, click listeners →
`App.i18n.setLocale(...)`) in `site/index.html`. The selector iterates
`App.i18n.SOPORTADOS` at runtime and consults `BOTONES_IDIOMA` to
resolve the button `id` — adding a language means adding a third
`<button>` and an entry in `BOTONES_IDIOMA` (§5, step 2).

## 2. Number format, money and clock: NOT just translation

These three points are the trickiest part of the system — translating
the word without touching the format produces a number or time that
reads wrong or just plain false:

- **Thousands/decimal separators**: Spanish uses `.` for thousands and
  `,` for decimals (`1.234,50`); English the other way around
  (`1,234.50`). See `assets/js/dinero.js` (`formatear()` with
  `DECIMAL_SEP`) as a living example — any activity that formats a
  number or amount needs the same per-locale branching, not a literal
  translation of the separator.
- **Numeric scale**: Spanish uses the long scale (1 000 000 000 = "mil
  millones", 1 000 000 000 000 = "un billón"); English uses the short
  scale (10⁹ = "one billion", 10¹² = "one trillion"). Translating
  "billón" as "billion" yields a number **one thousand times smaller**
  than intended. The `tools/numbers/` activity (which reads large
  numbers aloud) uses `es`/`en` arrays in `data.js` with genuinely
  different words (not a translated copy of the same list), plus
  per-locale group labels in `strings.<locale>.js` (Spanish needs
  `'miles de millones'`/`'billones'` as patches every 3 digits; English
  has one word per group: `thousand/million/billion/trillion`).
- **Clock**: "y cuarto"/"menos cuarto"/"y media" are not "and a
  quarter"/"less a quarter" in natural English — they are "quarter
  past"/"quarter to"/"half past". The `tools/clock/` activity (which
  reads the clock aloud) has a small `es`/`en` phrase table for these
  fixed expressions, not a word-by-word translation.

**General rule**: before literally translating any text that contains
a number, date, time or currency, check how a native speaker of the
target language would actually say it. If needed, the template may
have a different sentence structure per locale (e.g.
`'{euros} y {c} céntimos'` in Spanish vs. `'{euros} and {c} cents'` in
English — same order here, but do not assume it).

## 3. Cultural content (riddles, stories): NOT literally translated

A rule as strict as §2, but for text rather than numbers: **a riddle
translated word-for-word from Spanish stops working in English** — it
loses the rhyme, the double meaning or the cultural reference it
relied on. The version in each language has to be content **native to
that language**, with the same difficulty and pedagogical intent as
the original, not a translation of it.

- **`tools/riddles/`**: English riddles are word games or references
  that work in English, not the literal translation of the Spanish
  one.
- **`tools/stories/`**: stories have characters and situations natural
  to the reader's language and culture — proper names or geographic
  references change between `es` and `en`.

## 4. Binary `es`/`en` spots (to generalize when adding a language)

Reference grep: `grep -rn "locale() === 'en'" assets/ tools/`.

| File:line | What it does | What to change for a 3rd language |
|---|---|---|
| `assets/js/i18n.js:17` (`SOPORTADOS`) | `var SOPORTADOS = ['es', 'en'];` | Add the locale code: `['es', 'en', 'fr']` |
| `assets/js/i18n.js:87` (`BCP47` map) | `var BCP47 = { es: 'es-ES', en: 'en-US' };` | Add an entry: `fr: 'fr-FR'` |
| `assets/js/dinero.js:91` (`DECIMAL_SEP`) | `var DECIMAL_SEP = { es: ',', en: '.' };` | Add an entry with the new locale's decimal separator |
| `assets/js/dinero.js:95` (`formatear`) | uses `DECIMAL_SEP` | No change |
| `site/index.html` (buttons) + `BOTONES_IDIOMA` | 2 fixed buttons + id map | Add a third `<button>` + entry in `BOTONES_IDIOMA` |
| `sw.js` (`ARCHIVOS`) | lists the 2 `strings.<locale>.js` per activity | Add the new `strings.<locale>.js` per activity |
| `scripts/check.js` (`STRING_LOCALES`) | `var STRING_LOCALES = ['es', 'en'];` | Add the new code |
| `settings/app.js` (if it reads the active locale) | button/banner per locale | Generalize if needed |

## 5. Recipe: add a new language (example: French, `fr`)

Execute in this order. Each step is mechanical except for 4 (content)
and 5 (numbers/clock).

### Step 1 — Register the locale in the core

In `assets/js/i18n.js`:

```js
var SOPORTADOS = ['es', 'en', 'fr'];
var BCP47      = { es: 'es-ES', en: 'en-US', fr: 'fr-FR' };
```

Add `fr` to the `core`/`feedback` dictionary with the matching texts
(template in §1.2).

In `assets/js/dinero.js`, add the French decimal separator:

```js
var DECIMAL_SEP = { es: ',', en: '.', fr: ',' };
```

### Step 2 — Language selector in the landing

In `site/index.html`, add a third button inside `.idioma-selector`:

```html
<button type="button" class="btn-idioma" id="btnIdiomaFr" data-locale="fr" aria-pressed="false">🇫🇷 Français</button>
```

and in the `<script>` of the same page, add its entry to the
`BOTONES_IDIOMA` map (the listener and painting are already
generated in a loop over `App.i18n.SOPORTADOS`):

```js
var BOTONES_IDIOMA = { es: 'btnIdiomaEs', en: 'btnIdiomaEn', fr: 'btnIdiomaFr' };
```

### Step 3 — Landing: `site/strings.fr.js`

Create the `strings.fr.js` file with **the same keys** as
`strings.es.js` / `strings.en.js`:

```js
(function () {
  'use strict';
  App.i18n.register({
    title: 'Calculia',
    saludo: 'Bonjour. Que veux-tu pratiquer aujourd\'hui ?',
    modMates: '🧮 Mathématiques',
    modLogica: '🧩 Raisonnement et logique',
    numbers_nombre: 'Les Nombres',
    numbers_detalle: 'Compte, additionne et mesure.',
    // ... rest of keys translated to French
  }, 'fr');
})();
```

### Step 4 — Create `strings.fr.js` per activity (14 files)

For each `tools/<slug>/strings.es.js` and `tools/<slug>/strings.en.js`,
create the equivalent `strings.fr.js` with **the same keys** (same
names, same nested structure). The parity check from Step 7 will
verify it.

This is the most tedious step. Consider automating it in the future
with a generation script based on `strings.es.js`.

### Step 5 — French-specific format (numbers, clock, money)

Word-by-word translation is not enough (see §2):

- **Numbers**: French also uses the long scale like Spanish
  (10⁹ = "milliard"). Double-check `tools/numbers/data.js` — the
  English short scale does not apply.
- **Separators**: French uses a thin space (U+202F) for thousands
  and `,` for decimals. Update `DECIMAL_SEP` and, if needed, the
  thousands formatting in `tools/numbers/app.js`.
- **Clock**: "trois heures et quart" / "moins le quart" / "et demie" —
  write the keys thinking about how a native speaker would actually
  say it.
- **Money**: irregular plurals ("un euro"/"deux euros" but "un
  centime"/"deux centimes") and the decimal comma — verify
  `tools/wallet/app.js`.

### Step 6 — Update `sw.js` and `scripts/check.js`

Bump `VERSION` in `sw.js` and add `strings.fr.js` per activity to the
`ARCHIVOS` array. The regex in `scripts/check.js` (check #4) accepts
any locale configured in `STRING_LOCALES`; just add `'fr'` to the top
of that array.

### Step 7 — Verify key parity

`scripts/check.js` already validates that `strings.es.js`,
`strings.en.js` (and any other `strings.<locale>.js`) have
**exactly the same keys**. If you add `fr`, update `STRING_LOCALES`
in `scripts/check.js` to include `'fr'`:

```js
var STRING_LOCALES = ['es', 'en', 'fr'];
```

And run:

```bash
node scripts/check.js
```

If any key is missing in `fr`, `check.js` will list it with detail
("only in es", "only in en", "only in fr").

### Step 8 — Functional verification

- **Landing**: the third button changes the whole site and persists in
  `localStorage['calculia:locale']`.
- **Each activity** loads without console errors in the new locale.
- **`tools/numbers/`** and **`tools/clock/`** in particular: read
  aloud a couple of questions and check the number/time is correct
  per the locale's conventions (numeric scale, clock expressions,
  separators).
- **`tools/wallet/`**: check that the decimal separator and the
  spoken amount are correct.

## 6. What NOT to do

- Do not trust an automatic translation of numbers, dates, clock
  expressions or money without checking the actual convention of the
  locale (§2 and Step 5).
- Do not leave a key without its equivalent in every supported
  locale — the fallback to Spanish hides the gap instead of failing
  visibly. `scripts/check.js` fails if it detects the asymmetry.
- Do not use arrays in `strings.<locale>.js` for position/number-
  indexed data (`t()` flattens them with `join(', ')`); use an object
  with text keys (`{0:'', 1:'...'}`).
- Do not add a new language without first generalizing the binary
  `es`/`en` spots in §4 — otherwise the new locale will silently
  inherit English (or Spanish) behavior in number/clock/money format.
- Do not literally translate riddles, stories or any text that
  depends on wordplay, rhyme or cultural reference — write content
  native to the target language with the same difficulty and intent
  (§3).
- **Do not delete the monolithic `strings.js` files without updating
  `sw.js`**: the service worker caches the files listed in
  `ARCHIVOS`. After the multi-file refactor, `strings.<locale>.js`
  replace `strings.js` (bump `VERSION` to force a redownload).

## 7. Historical summary

- **v1.x (legacy, in Apptonomia)**: a single `strings.js` per activity
  with `{es: {...}, en: {...}}`. Simple, but mixed locales in every
  file and downloaded both to the client.
- **v2+ (Calculia from the start)**: multi-file system with
  `strings.<locale>.js`, synchronous load from `index.html` (no
  `document.write`). Keeps back-compat with the legacy `register(dict)`
  signature for smooth transitions. Direct migration from Apptonomia's
  design, no intermediate steps.
